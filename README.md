# Candidate Generation for Service Search

Решение задачи кандидатогенерации для поиска услуг. Для каждого поискового
запроса система должна выбрать из корпуса до 50 объявлений, которые затем могут
быть переданы модели ранжирования. Основная метрика — `Recall@50`: доля
релевантных объявлений, попавших в список кандидатов.

Результаты лучшей отправленной версии на закрытых тестах:

| Версия | Recall@50 |
|---|---:|
| Logistic Regression поверх четырёх retrieval-каналов | **0.722516** |

Подробное обоснование решеняи вынесено в
[`SOLUTION.md`](SOLUTION.md): использованные признаки, алгоритмы, локальная
валидация и найденные типы ошибок.

## Локальная валидация

Исходный `train.parquet` содержит только положительные взаимодействия: запрос и
объявление, которое пользователь выбрал. Для локальной оценки данные делятся по
полному поисковому контексту:

- `search_query`;
- `search_location_id`;
- `search_is_delivery_search`;
- `search_infm_params_text`;
- `search_category`.

Все строки одного контекста целиком попадают либо в development, либо в
validation. Это предотвращает прямое пересечение одинаковых запросов с теми же
фильтрами и локацией между частями выборки.


## Архитектура решения

Пайплайн состоит из двух этапов:

```text
Запрос
  ├── Local E5
  ├── Local TF-IDF
  ├── Nearby E5
  └── Global E5
          ↓
Объединённый пул кандидатов
          ↓
Logistic Regression
          ↓
До 50 item_id
```

### Текстовые представления

Текст запроса состоит из:

```text
search_query + search_infm_params_text
```

Для TF-IDF используется короткое представление объявления:

```text
item_title_raw + item_infm_params_text
```

Для E5 добавляется начало описания:

```text
item_title_raw + item_infm_params_text + первые 500 символов item_description_raw
```

Модель `intfloat/multilingual-e5-small` используется как bi-encoder. Запросы
кодируются с префиксом `query:`, объявления — с префиксом `passage:`. Эмбеддинги
нормализуются, поэтому скалярное произведение соответствует косинусной близости.

### Retrieval-каналы

#### 1. Local E5

Для запроса выбираются 40 семантически ближайших объявлений с совпадающими:

- `item_location_id == search_location_id`;
- `item_category_id == search_category`.

Это основной канал: большая часть пользовательских выборов относится к той же
локации, в которой выполнялся поиск.

#### 2. Local TF-IDF

Выбираются 40 ближайших объявлений по TF-IDF внутри той же пары
`(location_id, category_id)`. Этот канал дополняет E5 точными совпадениями:
редкими терминами, моделями, аббревиатурами и формулировками параметров.

#### 3. Nearby E5

Для каждого `location_id` восстанавливается медианная широта и долгота по
координатам объявлений. Затем выбираются до 20 семантически похожих объявлений:

- той же категории;
- из других `location_id`;
- на расстоянии не более 100 км.

Канал помогает в случаях, когда исполнитель находится в пригороде или соседнем
населённом пункте, но оказывает услуги в локации пользователя.

#### 4. Global E5

HNSW-индекс FAISS возвращает 100 семантически ближайших объявлений по всему
корпусу. Канал необходим для учета удалённых и редких услуг, где совпадение
локации не обязательно.

### Объединение каналов

После удаления повторов средний объединённый пул содержит около 170 кандидатов.
Его локальный Recall равен `0.8420`. Это верхняя граница для агрегатора: если
релевантного объявления нет ни в одном retrieval-канале, перестановка кандидатов
уже не сможет его вернуть.

Для каждой пары «запрос — кандидат» строятся 14 признаков:

- reciprocal rank в каждом из четырёх каналов;
- флаг присутствия в каждом канале;
- similarity-score Local E5, Local TF-IDF и Global E5;
- количество каналов, нашедших объявление;
- совпадение локации;
- совпадение категории.

Для обучения используются найденные релевантные объявления и до 20 случайных
нерелевантных кандидатов на запрос. Признаки стандартизуются, после чего
обучается логистическая регрессия с балансировкой классов.

На половине validation-запросов подбирался агрегатор, а вторая половина
использовалась только для сравнения методов:

| Метод агрегации | Локальный Recall@50 |
|---|---:|
| Фиксированные квоты | 0.785920 |
| Weighted RRF | 0.801750 |
| Logistic Regression | **0.809557** |
| HistGradientBoosting | 0.808100 |

После выбора метода логистическая регрессия переобучается на всех доступных
validation-запросах и используется для benchmark inference. В финальном top-50
сначала располагаются кандидаты правильной категории, затем остальные кандидаты
в порядке вероятности модели.

## Хронология экспериментов

Основную последовательность разработки можно проследить в блокнотах:

1. [`01_dataset_inspection.ipynb`](notebooks/01_dataset_inspection.ipynb) — структура Parquet-файлов, пропуски, частоты запросов и первичные наблюдения.
2. [`02_pipeline_development.ipynb`](notebooks/02_pipeline_development.ipynb) — построение локальной валидации, переход от отдельных retrieval-каналов к географическому гибриду, сравнение квот, RRF и обучаемого агрегатора.
3. [`03_benchmark_submission.ipynb`](notebooks/03_benchmark_submission.ipynb) — воспроизводимый inference отправленной версии и проверка `answer.csv`.


В конце development-блокнота сохранена краткая таблица ключевых локальных
результатов, поэтому ход улучшений можно посмотреть без повторного запуска всех
ранних тяжёлых экспериментов.

## Воспроизведение отправленной версии

Создать окружение и установить зависимости:

```bash
python3.12 -m venv venv
source venv/bin/activate
python -m pip install -r requirements.txt
```

Положить файлы в каталог `dataset/`:

```text
dataset/train.parquet
dataset/benchmark_queries.parquet
dataset/benchmark_items.parquet
```

Затем выполнить:

1. `02_pipeline_development.ipynb` — создаёт локальные retrieval-артефакты и обучает агрегатор.
2. `03_benchmark_submission.ipynb` — строит benchmark-кандидатов и сохраняет `answer.csv`.

TF-IDF-матрицы, E5-эмбеддинги, FAISS-индексы и retrieval-выдачи сохраняются в
`artifacts/`. При повторном запуске существующие артефакты загружаются с диска,
поэтому тяжёлые вычисления выполняются только при необходимости.

## Анализ ошибок

При анализе были найдены следующие типы ошибок.

### Синонимы и разные формулировки

TF-IDF не связывал выражения вроде «прокат автомобиля» и «аренда автомобиля».
Для таких случаев был добавлен семантический E5-канал с заголовком, параметрами
и частью описания объявления.

### Похожие услуги из других городов

Глобальный семантический поиск часто возвращал текстуально похожие объявления
из нерелевантных регионов. Поэтому основным стал Local E5 с точным совпадением
локации и категории.

### Слишком строгое совпадение location_id

Часть релевантных исполнителей находилась в пригородах или соседних локациях.
Полный отказ от географического фильтра добавлял много шума, поэтому был создан
отдельный Nearby E5-канал с радиусом 100 км.

### Удалённые и редкие услуги

Для онлайн-услуг, производства и доставки местоположение исполнителя может быть
неважно. Чтобы локальные ограничения не теряли такие объявления, сохранён канал
Global E5.

### Редкие термины и точные параметры

Семантическая модель иногда уступала буквальному совпадению в названиях моделей,
аббревиатурах и узких терминах. Local TF-IDF был оставлен отдельным каналом, а
агрегатор научился учитывать сигналы обеих моделей.

### Ошибки категории

Почти все релевантные пары имеют одинаковую категорию, но глобальный retrieval
иногда возвращал кандидатов из соседних категорий. Совпадение категории было
добавлено как признак, а в финальном top-50 кандидаты правильной категории
размещаются первыми.
